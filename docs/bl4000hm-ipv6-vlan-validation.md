# BL4000HM配下のIPv6 VLAN検証（識別情報マスク版）

検証日：2026年11月14日。対象：auひかり、BL4000HM、ファームウェア1.0.8。

## 結果

この環境では、HGWへのDHCPv6-PD要求は `NoPrefixAvail` で拒否された。一方、HGWに静的ルートを登録し、下位ルーターの各VLANに別々の `/64` を設定すると、2つのVLANでSLAACによるアドレス自動設定とIPv6インターネット通信に成功した。

| 検証                                        | 結果                             |
| ------------------------------------------- | -------------------------------- |
| DHCPv6による端末向けアドレス要求（IA_NA）   | アドレス提示あり。正式取得も確認 |
| 下位ルーター向けプレフィックス要求（IA_PD） | Status Code 6（NoPrefixAvail）   |
| 静的ルート経由の別サブネットからの通信      | IPv6 ping・HTTPS成功、NAT66なし  |
| VLAN 10・20の802.1Qタグ                     | トランク上のパケットで確認       |
| 各VLANのアドレス・デフォルト経路            | RA/SLAACで自動設定               |
| 両VLANからの外部通信                        | IPv6 ping・HTTPSとも成功         |

これは一環境・一時点の実測であり、BL4000HM全般のPD非対応や、回線に割り当てられた範囲全体を示すものではない。PD失敗の根本原因は未確定。

## 匿名化と記載範囲

契約者のIPv4/IPv6アドレス、MACアドレス、機器シリアル、電話番号、SSID、ログイン情報、固有ホスト名、ローカルパスは掲載しない。実際のグローバルIPv6アドレスは文書用の `2001:db8::/32` 内へ置換し、インターフェースIDも架空の値にした。リンクローカルアドレスは役割に対応する例示値へ置換した。公開DNSサービスの共通アドレス、機種・ソフトウェアの版、VLAN IDは残している。

以下の設定とログは識別情報を置換した抜粋・要約であり、生ログではない。`2001:db8::/32` はインターネット疎通の試験に使えるアドレスではない。

| 役割                                       | 文書内の例示値          |
| ------------------------------------------ | ----------------------- |
| HGW直下のLAN                               | `2001:db8:1234:1::/64`  |
| HGWのリンクローカルアドレス                | `fe80::1`               |
| 検証ルーター上流側のリンクローカルアドレス | `fe80::2`               |
| VLAN 10                                    | `2001:db8:1234:10::/64` |
| VLAN 20                                    | `2001:db8:1234:20::/64` |

この例示用の番号付けは、実回線への `/56` 等の割当を意味しない。VLAN IDとIPv6サブネット番号を一致させる必然性もない。

## 検証環境と構成

有線接続のNixOS検証機に、一時的なLinux network namespaceを作成した。HGWへの接続は物理NIC上のmacvlan、内部の接続はvethを使用した。ホスト本体の既存経路・転送設定は変更していない。TailscaleはSSH操作に使ったが、検証パケットは独立したnamespaceから有線LANへ送信した。

```text
インターネット
      |
 auひかり / BL4000HM
 静的ルート：VLAN 10・20の /64 → fe80::2、LAN側
      |
 有線LAN（HGWとの間はタグなし）
      |
 +------------------ NixOS検証機 ------------------+
 |                                                  |
 |  ルーターnamespace                                |
 |    上流：macvlan、リンクローカルアドレスのみ       |
 |    下流：rtr.10 / rtr.20、各 /64 の ::1            |
 |    IPv6 forwarding + radvd                        |
 |              |                                   |
 |    802.1Qトランク（VLAN 10・20、veth）             |
 |              |                                   |
 |  スイッチnamespace                                |
 |    Linux bridge、VLAN filtering有効               |
 |       +-- access VLAN 10 -- 端末namespace 10       |
 |       +-- access VLAN 20 -- 端末namespace 20       |
 |                                                  |
 +--------------------------------------------------+
```

物理スイッチ・APにはVLAN設定をしていない。Linuxの802.1Qインターフェースと仮想スイッチを使った検証であり、導入予定の機器との互換性試験ではない。

## DHCPv6-PDの検証

HGWの設定2・自動構成・保存済みを管理画面で確認した。再起動後もIA_PDは拒否された。設定3に変更したとの利用者申告後にも再試験し、同じ応答を確認した。ただし設定3への変更後の画面値自体は、この再試験では再確認していない。

試した条件：

- IA_PD単独、IA_NAとの同時要求、IA_NA正式取得後の同じクライアントからの要求。
- IA_PDを1個または複数要求。IAID 0・1・2などを使用。
- 希望サイズの指定なし、および `/56`・`/60`・`/64`。
- DUID-LL・DUID-LLT、異なる検証用MACアドレス。
- 独自のパケット検証プログラムとdhcpcd 10.3.2のテストモード。

結果はIA_NAへのアドレス提示と、IA_PDへの `NoPrefixAvail`。dhcpcdにも `DHCPv6 REPLY: No Prefix Available` のログがあった。dhcpcdはnamespace固有のDUID保存先について警告を出したが、要求送信と応答受信はできており、独自プログラムの結果とも一致した。正式取得した検証用IA_NAリースはReleaseし、成功応答を確認した。

HGWの管理画面には、上流の委譲範囲やPDプールを確定できる情報が見当たらなかった。LAN側の `/64` 表示や、WAN情報APIのプレフィックス欄が空であることから、回線全体の割当サイズを断定することはできない。

## 静的ルートによる単一サブネットの検証

HGW直下のLANとは別の `/64` を検証用に仮置きし、ルーターnamespaceと端末namespaceを接続した。この段階では端末アドレスを手動設定した。HGWには、その `/64` 宛てを検証ルーターのリンクローカルアドレスへ転送する静的ルートを1件登録した。

端末からHGW、Cloudflare（`2606:4700:4700::1111`）、Google（`2001:4860:4860::8888`）へのpingは、それぞれ3回すべて成功した。CloudflareのHTTPS `/cdn-cgi/trace` にも証明書検証を有効にしたまま接続でき、外部で観測された送信元が端末に設定したIPv6アドレスと一致した。NAT66は使用していない。

HGWの静的ルートを削除すると、同じ端末からCloudflareへのpingは2回とも失敗した。追加した経路が往復通信の成立に必要だったことを確認した。

## 2つのVLANとRA/SLAACの検証

### HGWの静的ルート

| 宛先ネットワーク（置換済み） | ネクストホップ（置換済み） | インタフェース |
| ---------------------------- | -------------------------- | -------------- |
| `2001:db8:1234:10::/64`      | `fe80::2`                  | LAN            |
| `2001:db8:1234:20::/64`      | `fe80::2`                  | LAN            |

登録により即時適用し、恒久運用の設定としては保存しなかった。ルーターnamespaceのデフォルト経路はHGWのリンクローカルアドレスを指定した。

### スイッチとルーター

トランクポートにはVLAN 10・20をタグ付きで設定した。各端末側ポートには、それぞれのVLANをPVID・タグなし送出として設定した。ルーターには `rtr.10` と `rtr.20` を作り、各VLANの `/64` 内の `::1` を設定した。

radvd 2.21をルーターnamespaceで起動した。以下はVLAN 10の設定例であり、VLAN 20にも対応する別プレフィックスで同じ設定を行った。

```text
interface rtr.10 {
    AdvSendAdvert on;
    MinRtrAdvInterval 3;
    MaxRtrAdvInterval 10;
    prefix 2001:db8:1234:10::/64 {
        AdvOnLink on;
        AdvAutonomous on;
        AdvValidLifetime 600;
        AdvPreferredLifetime 300;
    };
    RDNSS 2606:4700:4700::1111 {
        AdvRDNSSLifetime 60;
    };
};
```

短い広告間隔・有効期間は一時検証用であり、本番運用の推奨値として示したものではない。

### 観測結果

端末にはグローバルアドレスもデフォルト経路も手動設定していない。LinuxカーネルがRAを受信し、SLAACアドレスとデフォルト経路を生成した。

| 項目                         | VLAN 10                      | VLAN 20                      |
| ---------------------------- | ---------------------------- | ---------------------------- |
| 自動生成アドレス（置換済み） | `2001:db8:1234:10::a/64`     | `2001:db8:1234:20::b/64`     |
| アドレスの表示               | `dynamic`、`proto kernel_ra` | `dynamic`、`proto kernel_ra` |
| デフォルト経路               | `proto ra`                   | `proto ra`                   |
| CloudflareへのIPv6 ping      | 2回中2回成功                 | 2回中2回成功                 |
| HTTPS trace                  | 成功、HTTP/2・TLS 1.3        | 成功、HTTP/2・TLS 1.3        |
| 外部で観測された送信元       | 自動生成アドレスと一致       | 自動生成アドレスと一致       |

tcpdump 4.99.7でトランクを観測し、802.1QのVLAN ID 10・20、それぞれのRA、対応する `/64` のPIO（onlink・autonomous）、RDNSSオプションを確認した。

HTTPS検証はIPv6リテラル宛てで実施した。DNS情報がRA内で通知されたことは確認したが、端末namespaceにDNS管理デーモンは導入しておらず、DNS設定の自動反映や名前解決は未検証。

## 結論と残る制約

実測から、この回線では少なくとも試した2つの別 `/64` に対して、静的ルート経由の往復通信が成立した。PDを使わず、各VLANにRA/SLAACでIPv6を配布する構成は動作した。

ただし、以下はこの検証から保証できない。

- **正式な割当範囲と継続利用**：試験プレフィックスは仮置きであり、KDDIから割当範囲の確認を得ていない。疎通成功は `/56` 全体の利用権限・将来の継続動作を示さない。
- **PD拒否の根本原因**：HGW内部のPDプール・実装・配布条件のどれが原因かは未確定。機種全般の非対応とは結論づけない。
- **実機への適用**：物理スイッチ、Wi-Fi AP、スマートフォン等での動作・性能・再起動後の復旧は未検証。
- **VLAN間の通信制限**：今回のルーターはIPv6転送を有効にしている。VLANを分けるだけではルーター経由の相互通信を遮断しない。本番ではIPv6ファイアウォールが必要。
- **運用時の追従**：静的設定は回線プレフィックスの変更に自動追従しない。変更時にはHGWの経路、各VLANのアドレス・RA設定等の更新が必要。

## 後片付け

HGWに追加した静的ルートは全件削除し、一覧が空、変更を保存するボタンが無効の状態に戻ったことを確認した。管理画面からログアウトし、ブラウザーを閉じた。

検証用radvdを停止し、namespace・macvlan・veth・VLANインターフェース・一時設定ファイルを削除した。既存ホストの経路・転送設定は変更していない。radvdとtcpdumpはNix storeに取得したが、システムの宣言的設定や常駐サービスには追加していない。恒久構成は導入していない。
